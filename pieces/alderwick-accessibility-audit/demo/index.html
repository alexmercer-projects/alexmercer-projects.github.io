Scope and method

What was checked, and how

The pages were picked around the tasks patients come to do: find a doctor, book, log in, pay, and fill in the intake form. Each one goes through the same six checks. For this demo the site is fictional, so this describes the method, not results from real testing.

  1. 01

    Automated scan

    Run axe-core and Lighthouse on every page at desktop and phone widths. A scan catches roughly a third of issues, so it’s where the audit starts, not where it ends.

  2. 02

    Keyboard pass

    Use every page with only Tab, Shift+Tab, Enter, Space, Esc and the arrow keys. Can you reach everything, see where you are, and get out of every popup?

  3. 03

    Screen reader pass

    Book an appointment and log in with NVDA and Firefox on Windows and VoiceOver and Safari on iPhone. Check names, roles, headings, links and error messages.

  4. 04

    Zoom and reflow

    Zoom to 200% and 400%, and check the layout at 320 CSS px wide. Turn on the text-spacing overrides and look for clipped or overlapping text.

  5. 05

    Color and contrast

    Measure text and control colors with a contrast checker, and check that no information depends on color alone.

  6. 06

    Documents and media

    Check PDFs with a PDF accessibility checker and the reading-order tools in a PDF editor. Check videos for captions and transcripts.

Fixes

Before and after, in code

The fixes most teams ask about, written against the clinic’s example markup. The same patterns work in WordPress, Squarespace code blocks or any hand-built site.

1.1.1 Non-text Content (A) Findings #04

Text alternatives

Decide what each image is for. A photo next to the doctor’s name adds nothing for a screen reader, so it gets an empty alt. An image that holds information needs that information as text.

1.4.3 Contrast (Minimum) (AA) Findings #05, #06

Color contrast

Both pairs keep the clinic’s look but get dark enough to read. These ratios are computed with the WCAG relative-luminance formula and truncated, not rounded up.

Before #9a9a9a on #ffffff

2.81:1 fails 4.5:1

After #5c6670 on #ffffff

5.85:1 passes 4.5:1

Before #ffffff on #3fb8af

2.41:1 fails 4.5:1

After #ffffff on #1f6f69

5.93:1 passes 4.5:1

3.3.2 Labels or Instructions (A) Findings #02

Form labels

Placeholders aren’t labels. A visible label stays put, is read by screen readers, and gives voice-control users a name to say (“click First name”).

2.4.7 Focus Visible (AA) Findings #07

Visible focus

Don’t remove the outline. Replace it with one that’s easier to see than the browser default, and only show it for keyboard focus.

2.1.2 No Keyboard Trap (A) Findings #01

Keyboard trap in the booking window

A modal should hold focus while it’s open, but there always has to be a way out. The native <dialog> element gives you Esc to close and a proper modal state.

1.3.1 Info and Relationships (A) Findings #12

Heading structure

Screen reader users jump between headings to scan a page, the way sighted people scan bold text. The levels should describe the outline, and CSS should handle the size.

2.4.4 Link Purpose (In Context) (A) Findings #13

Link purpose

Every link should make sense on its own, because that’s how screen readers list them. Usually the best fix is to make the card title the link.

PDF remediation

The intake form, step by step

PDFs on a website fall under the same WCAG criteria as the pages. For a form patients have to fill in, the questions to ask are whether a screen reader can read it in the right order and whether every field says what it wants.

Retag or rebuild?

A 4-page form that changes once a year is worth retagging. If it changes often, rebuild it as an accessible web form that emails the clinic, and the PDF problem goes away.

  1. 1

    Fix the source first

    If the Word or InDesign file exists, use real headings, lists and table headers there and export with tags turned on. That beats tagging by hand after the fact.

  2. 2

    Tag the structure

    Every block gets the right tag: H1 to H3 for headings, P for text, L and LI for lists, Table with TH header cells. Page numbers, rules and other decoration are marked as artifacts so they’re skipped.

  3. 3

    Set the reading order

    Order the tags so the left column is read fully before the right one, and every label comes right before its field. Check it with the reading-order tool and by listening with a screen reader.

  4. 4

    Name every form field

    Give each of the 38 fields a tooltip (the TU entry) that a screen reader reads aloud, like “Date of birth, MM/DD/YYYY”. Set the tab order to follow the structure, and group radio buttons under one name.

  5. 5

    Describe images, set properties

    Add alt text to the logo and the body diagram. Set the document title, show it in the title bar instead of the file name, and set the language to English.

  6. 6

    Check, then check by hand

    Run a PDF/UA checker and the built-in accessibility check in a PDF editor, then fill in the whole form with NVDA and with the keyboard only. Automated checks pass plenty of PDFs that are still unusable.

About this report

This is a concept demo of the audit reports I write. Alderwick Family Clinic, its website and its intake form are made up. Nothing was scanned or tested, and every finding, count and estimate is an example. The WCAG 2.2 success criteria, levels and contrast math are real.

An audit is a snapshot of how a site works against WCAG on the day it’s checked. It isn’t a legal opinion or a certification.

This page was built to the same standard: real headings in order, a skip link, visible focus, text contrast of at least 4.5:1 (the two “before” swatches above are pictures of the failing colors, on purpose), and a findings table that works without JavaScript. It was checked with axe-core and a keyboard pass.
